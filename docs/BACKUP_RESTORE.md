# Supabase Lite: зашифрованные резервные копии и восстановление

**Статус:** готова локальная упаковка и проверка целостности; **полный restore не реализован и не испытан**. Универсальный Core Compose также ещё не готов. Нельзя считать это производственным backup решением до E2E теста.

## Что входит

- `database.dump`: `pg_dump -Fc` одной прикладной БД, включая схемы auth/public/storage, если права экспорта достаточны.
- `storage.tar`: локальные файлы backend Storage (только если STORAGE_DIR действительно соответствует используемому backend; S3 потребует другого механизма).
- `SHA256SUMS` и `manifest.json`: внутренние проверки, версия формата, время, имя БД.
- Все файлы вместе зашифрованы `age` на **публичный** recipient. Приватный ключ age хранится вне GitHub/VDS.

**Ограничения:** `pg_dump` сам по себе не содержит глобальные роли, конфигурацию Docker/Envoy/SMTP/Nginx, секреты, применённые миграции вне дампа и образа Edge Functions. Для восстановления нужны привязанные к конкретному релизу версии Core и отдельное защищённое хранилище конфигурации/секретов. PostgreSQL и Storage должны соответствовать одному состоянию. На работающей системе согласуйте паузу записи/консистентный snapshot; иначе архив может содержать несовпадающие метаданные и файлы.

## Предварительная настройка

1. Установить `pg_dump` совместимой версии PostgreSQL, `age`, `tar`, `sha256sum`, `python3`; права только на чтение исходных данных.
2. Сгенерировать **отдельный** age keypair и сохранить приватный identity в другом защищённом месте, не коммитить его и не передавать в GitHub Actions.
3. На отдельном хранилище выбрать `OUTPUT_DIR`, недоступный анонимным пользователям. Хранить минимум одну копию вне VDS.
4. Подготовить `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGPASSWORD` безопасно через окружение оператора (не CLI/логи/историю).
5. Установить `STORAGE_DIR` в фактический каталог файлов Supabase Storage; подтвердить backend не S3.

## Пример (плейсхолдеры, не вставлять секреты в shell history)

```bash
export AGE_RECIPIENT='age1…'
export PGHOST='127.0.0.1'
export PGUSER='backup_reader'
export PGDATABASE='postgres'
export STORAGE_DIR='/srv/isolated-lite/storage'
export OUTPUT_DIR='/srv/offsite-staging'
# PGPASSWORD вводит оператор скрыто / через внешний secret manager.
bash scripts/backup-core.sh
bash scripts/verify-backup.sh /srv/offsite-staging/ARCHIVE.tar.age /secure/age-identity.txt
```

`verify-backup.sh` подтверждает только целостность архива и читаемость списка PostgreSQL, **не** полноценную восстанавливаемость. Не публиковать дампы или открытые данные даже в приватном GitHub.

## Обязательный независимый restore-тест перед релизом

- [ ] Создать отдельный Docker project с **новыми** volumes, не связанными с действующим VDS.
- [ ] Поднять совместимые версии PostgreSQL, GoTrue/PostgREST/Storage и системные роли.
- [ ] Расшифровать архив в закрытый временный каталог, проверить SHA.
- [ ] Восстановить `database.dump` в чистую БД совместимым `pg_restore`, развернуть Storage файлы в независимый backend.
- [ ] Сверить users, identities, profiles, RLS, публикации, Storage objects и физические файлы, работоспособность Auth/REST/Storage.
- [ ] Проверить, что старые токены не восстановлены без согласованного secret escrow.
- [ ] Зафиксировать PASS и удалить изолированные тестовые ресурсы.
- [ ] Проверить периодическое выполнение, retention, offsite upload и оповещение о сбоях; **не** удалять действующие бэкапы, пока новые не проверены.

## Связь с CI/CD

GitHub Actions может **инициировать** backup с ограниченными правами, но ключ расшифровки не хранить в Actions. Двоичные архивы в git историю не добавлять. GitHub использовать для manifest/скриптов и release metadata; encrypted archive — во внешнем объектном хранилище или приватном release при соблюдении лимитов. Не включать автоматическую замену production до первого независимого restore PASS.
