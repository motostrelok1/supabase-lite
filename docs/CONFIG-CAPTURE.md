# Снятие обезличенной конфигурации с действующего VDS

Источник истины — **два фактических Compose-файла** установленного стека и список образов контейнеров, а не шаблон из интернета.

## Важно
Перед публикацией нужно вручную просмотреть каждый YAML-файл: даже `docker-compose.yml` и `docker-compose.override.yml` могут содержать inline-секреты, приватные IP/домены, пути и service role key. **Не публикуйте вывод `docker compose config`**: он подставляет значения из `.env`.

Команды для локального просмотра без раскрытия значений секретов:

```bash
cd /opt/supabase
docker compose -f docker-compose.yml -f docker-compose.override.yml config --services
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
```

Не публикуйте содержимое `.env` и полную конфигурацию с уже подставленными значениями. Для сборки публичного шаблона заменяйте все потенциальные секреты плейсхолдерами `${VARIABLE_NAME}`; даже секретные значения в комментариях запрещены.

## Критерии переносимости
- Все окружения создают собственные уникальные секреты.
- Имена контейнеров, сетей и томов не пересекаются с существующим стеком.
- Каталог установки выбирается пользователем, без жёсткого `/opt/supabase`.
- Прокси/HTTPS не меняют существующую конфигурацию без подтверждения.
- Образы фиксированы, данные сохраняются в persistent volumes.
- Есть тест установки с нуля и тест восстановления данных.
