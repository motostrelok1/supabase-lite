# Supabase Lite — техническое задание и план v0.1.0

Обновлено: 2026-10-16. Репозиторий: `motostrelok1/supabase-lite`.

## Главный продуктовый сценарий: новая автошкола под ключ

**Целевой запрос:** если сторонняя организация хочет собственную копию автошколы, оператор запускает новый VDS, устанавливает Supabase Lite с профилем `driving-school`, публикует PWA и получает работающее приложение с **пустой прикладной БД, но полной схемой, политиками, функциями, триггерами, бакетами и настройками**. Пользователей, занятий, финансов и файлов исходной автошколы в новой установке нет.

### Два режима поставки
1. **Core:** универсальные семь сервисов Supabase Lite, без таблиц и логики конкретного проекта.
2. **Driving School Kit:** Core + **версионированный прикладной пакет** из репозитория `motostrelok1/driving-school` + самостоятельная сборка/развёртывание PWA. Один оркестратор устанавливает оба пакета последовательно и проверяет совместимость версий.

**Важно:** нельзя считать `pg_restore --schema-only` из облачного backup воспроизводимым установщиком. Источником истины должны стать проверенные, упорядоченные SQL migrations и setup scripts, включающие **зависимости вне public** (например триггер на `auth.users`, права системных ролей, storage policies, функции). Существующий дамп пригоден для сверки инвентаризации, не как долгосрочная зависимость от конкретного клиента.

### Контракт установки Driving School
1. Preflight: ресурсы VDS, DNS/TLS, свободные порты, Docker/Compose, версии образов; отказаться от запуска при конфликте с другой инсталляцией.
2. Создать уникальный идентификатор инсталляции, секреты и **изолированные** сети/тома PostgreSQL и Storage; публично только HTTPS gateway и PWA.
3. Поднять Core, дождаться readiness каждого сервиса.
4. Применить все schema migrations приложения **с нуля**, включая 30 исходных таблиц, функции, RLS, индексы, FK, триггеры, grants, системные связи Auth и бакеты; сверять структуру с актуальной версией репозитория, не считать прежние численные инвентаризации неизменяемыми.
5. Развернуть Edge Functions, realtime publication, SMTP провайдер или безопасный mailpit режим, cron и уведомления с **новыми** ключами/параметрами. Пуши и SMTP реальным получателям — только после отдельной настройки и разрешения.
6. Собрать/развернуть PWA с `VITE_SUPABASE_URL` и публичным anon key новой инсталляции; никогда не включать service_role key в клиент.
7. Bootstrap первого администратора через защищённую одноразовую процедуру, без обхода триггеров в обычной эксплуатации, без заранее известных паролей.
8. Smoke tests полного пути через HTTPS: регистрация → профиль → роли/RLS → группа → instructor → урок/расписание/запись → файлы → сообщения/Realtime → Functions. Negative tests по запретам доступа; без реальных уведомлений.
9. Записать manifest инсталляции (версии Core, schema/app, выполненные миграции), создать backup и инструкцию по восстановлению. Провал любого шага должен блокировать отметку готовности.

### Масштабирование
- **Первая цель:** multi-instance (один независимый Docker project/набор томов/секретов на отдельную организацию, отдельный домен и PWA). Это простое горизонтальное масштабирование числа **инсталляций**, а не кластеризация одного экземпляра.
- **Позже:** multi-tenant или кластерные Postgres/Storage/Realtime, очередь заданий, центральная панель инсталляций, обновления сотен экземпляров — отдельный проект с требованиями по нагрузке и отказоустойчивости.
- Автоматические обновления должны иметь version pin, миграции, backup, rollback plan и проверку совместимости версии PWA и backend.

### Критерий готовности «поделиться автошколой»
На **новом** VDS без заранее восстановленной схемы/данных: один документированный запуск создаёт полностью самостоятельный Core + Driving School PWA; роль администратора создаётся безопасно; все сценарии автоматического smoke test проходят; восстановление после backup проверено; из исходной автошколы не импортировано ни одной персональной записи. Время «несколько минут» — целевой UX, измерить фактически после первой чистой установки, не обещать заранее.

## Цель и границы
Поставляемый отдельно от автошколы минимальный self-hosted Supabase: воспроизводимое развёртывание с нуля на VDS через Docker Compose, генерацией индивидуальных секретов, безопасным обновлением и документированным восстановлением. Это **не** копия БД Driving School: прикладные таблицы, политики и миграции устанавливает проект-потребитель отдельно. Не переносить пользователей, файлы, ключи, адреса и резервные копии действующей автошколы.

## Целевой состав
1. PostgreSQL (с системными ролями и схемами Supabase).
2. Auth / GoTrue.
3. PostgREST.
4. Realtime.
5. Storage API и локальный файловый backend.
6. Edge Functions runtime.
7. Envoy API Gateway с маршрутами `/auth/v1`, `/rest/v1`, `/storage/v1`, `/realtime/v1`, `/functions/v1`.

Опциональные компоненты: тестовый Mailpit, мониторинг, HTTPS через внешний Nginx/reverse proxy. Studio, Postgres Meta, imgproxy, Supavisor не включать в базовый профиль. Образы закреплять точными проверенными версиями или digest, не `:latest`.

## Уроки эксплуатации Driving School — что перенести в универсальный продукт
- В тестовой среде Driving School уже проверены отдельная БД, регистрация GoTrue, refresh/logout/recovery, PostgREST и Mailpit. Это **результат другого репозитория**, а не доказательство готовности Lite.
- При создании PostgreSQL обязательно согласовывать пароли ролей `authenticator` и `supabase_auth_admin` с секретами окружения **до** запуска API.
- Тестовый Docker bridge `internal: true` в использовавшемся Docker 29.9.1 не дал host-публикацию портов. Проверенный обход в проекте — локальные dual-homed socat-прокси. Для Lite выбрать и проверить устойчивую сетевую архитектуру отдельно; публиковать API только через заданный gateway, администрирование — localhost/SSH-туннель.
- Изолировать исходящие подключения Auth/Functions, письма и внешние webhook по профилю: локальный Mailpit для тестов без настоящей отправки.
- SQL-триггер `handle_new_user` и схема `public.profiles` **специфичны для Driving School**, не копировать их в универсальный образ.

## Контракт установки
- `install`: только в пустой Docker project/volumes; проверка портов, RAM/disk, версий Docker/Compose, конфликтов и существующих томов; при конфликте завершать без изменений.
- `config`: генерация JWT signing secret, anon/service_role keys, DB passwords и иных обязательных секретов отдельно для каждого окружения; локальный файл с правами 0600; никакие секреты в Git/логи/CLI-аргументы.
- `verify`: health endpoints и SQL-проверки, положительные и отрицательные Auth/REST/Storage запросы, smoke test Realtime/Functions, без внешних писем и пушей.
- `backup`/`restore`: PostgreSQL + Storage metadata + бинарные объекты + секреты по защищённой процедуре; доказательство восстановления на независимых томах.
- `upgrade` и `rollback`: закреплённые версии, совместимость миграций, резервная копия до изменения, возможность безопасного отказа от обновления; не обещать rollback PostgreSQL без реального теста.
- `uninstall`: по умолчанию останавливает сервисы **без удаления данных**; destructive wipe только с отдельным явным подтверждением.
- HTTPS: пример настройки reverse proxy и TLS, не затрагивая существующие конфигурации других сайтов.

## Безопасность
- По умолчанию не выставлять PostgreSQL/Storage internals/SMTP в публичную сеть.
- Раздельные тестовые и рабочие окружения, никакого доступа по volume/network к существующим сервисам.
- Проверять scopes JWT и роли БД; service_role не использовать в браузере.
- Запретить реальные письма, push, cron/побочные эффекты в smoke-тестах.
- Секреты прошлого тестового стека не переиспользовать; при утечке ротировать.
- Конфигурация Lite должна быть независима от конкретного домена или приложения.

## Критерий готовности v0.1.0
Новый VDS/чистый Docker project → установка из репозитория с новой парой секретов → все семь сервисов отвечают и поддерживают базовые сценарии → перезапуск сохраняет данные → backup/restore успешно протестированы → TLS и RLS задокументированы. Пока эти критерии не выполнены, статус «шаблон, не готов к установке».
